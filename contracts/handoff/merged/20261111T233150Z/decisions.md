### D-?: Add record.v2 and gold.v2 as NEW versions next to v1 (route, strength, formulation, age, status...)   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: The simulated clinical review of m3 (D-122) showed that our record format (record.v1) has no place for the route ("injection" or "by mouth"), the strength of a syrup (120 mg per 5 ml), the child's age or weight, "as needed", "before/after food", or whether a drug was prescribed now or only taken in the past. Without these fields three CRITICAL error classes (CR-ROUTE, CR-PAEDIATRIC, CR-LIQUID-STRENGTH) can never be measured. How do we add them without breaking the eight modules that already use v1?
- Options we considered: (1) Change record.v1 in place. Pro: one format. Con: every module and test breaks at once; the brief forbids changing a contract without a version bump. (2) Add an optional "extensions" object to v1. Pro: nothing breaks. Con: the safety fields would be optional and easy to forget; v1 would no longer mean one thing. (3) A new version, record.v2 (and gold.v2, because the scorer compares records with gold), living NEXT TO v1. Pro: nothing existing breaks; modules move one at a time; the new fields are required (null when not said), so they cannot be silently forgotten. Con: two versions exist for a while; a converter is needed.
- What we chose: Option 3. Per medication: route, strength_value + strength_unit (separate from the dose amount), formulation, as_needed, food_timing, status, speaker and field_evidence (one evidence span per filled-in new field). Per advice: speaker. Per record: patient_age_band and weight_kg, each either null or a value with evidence.
- Why: A record that says "ceftriaxone 1000 mg" without "injection", or "10 ml" without the syrup strength, can mislead a prescriber. Putting the fields in a new version fixes the root cause while the old version keeps working. The bare name "record" still means v1, so no module changes meaning by accident.
- What we actually did: contracts/schemas/record.v2.schema.json, contracts/schemas/gold.v2.schema.json; new rules in contracts/validate.py; fixtures in fixtures/record.v2/ (11 valid, 9 invalid) and fixtures/gold.v2/ (9 valid, 5 invalid), generated by fixtures/build_fixtures.py, including a child syrup example, an injection example and a past-tense "already taken" example; tests/test_record_v2.py (43 tests). Field table and per-module notes: contracts/README.md. Run `uv run python -m contracts.validate --check-fixtures fixtures` and `uv run pytest tests -q`.
- What could go wrong / weaknesses: Until m3, m4, m5, m6 and the m7 scorer switch to v2 the three classes stay "not measurable". The fixture doses and Kannada sentences are illustrative, not native-validated and not clinically checked. The clinical review that asked for these fields is ai_simulated_review, not a real clinician.
- What else could be done: Add a paediatric weight-based dose table from a fetched national source so the verifier can really check child doses; add a "dose_basis" (per kg) field later if a real clinician asks for it.
- How to change this decision later: add record.v3 the same way (new schema file, CHANGELOG entry, fixtures, migrator); never edit a published version.
- Status: done (contract); module migration not done (Phase C)

### D-?: "negated" keeps only its grammar meaning; a new "status" field says what happened with the drug   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: In v1, `negated: true` on a drug could mean "do not take it", "it was not taken", or "the course was not finished" (D-122 finding M3-M1). A reader would assume "no exposure", which can be wrong. How should v2 say what actually happened?
- Options we considered: (1) Keep only `negated`. Pro: simple. Con: the dangerous ambiguity stays. (2) Replace `negated` by a status. Pro: one clear field. Con: the negation checks (m3 table, m4 C3) and the CR-NEG scoring use `negated`; removing it breaks them. (3) Keep `negated` for "the sentence is negated" and add `status` with the clinical meaning: prescribed, already_taken, not_taken, advised_against, stopped_early, continue_existing, unknown.
- What we chose: Option 3. We added `not_taken` to the requested list: "did the child drink the syrup? / no" is neither "advised against" nor "unknown", and the reviewer listed it.
- Why: Grammar (is there a "not"?) and clinical meaning (was it given?) are different questions; mixing them caused the bug. Any status other than "unknown" must point at the words that justify it.
- What we actually did: `status` and its evidence rule in record.v2/gold.v2 and validate.py; fixture rec2-fx-asha-002 (not_taken, cross-turn "ಇಲ್ಲ"), rec2-fx-past-009 (already_taken and advised_against). The severity note says which status mix-ups count as CR-NEG.
- What could go wrong / weaknesses: Deciding status from Kannada past tense or a "-ಬೇಡಿ" ending is a language rule that is not native-validated. Some cases may fit two statuses; then "unknown" is the honest answer.
- What else could be done: ask a real clinician whether "partly taken" needs its own value.
- How to change this decision later: add a value to the status enum in a new schema version; update docs/severity.md mapping note.
- Status: done

### D-?: Reject hidden text-direction characters (bidi controls) in v2 records   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: The m6 security audit (D-123, finding F6) showed that Unicode "bidi control" characters (U+202A..U+202E, U+2066..U+2069) can make text DISPLAY differently from what is stored, for example "after food" shown where "before food" is stored. Where do we stop them?
- Options we considered: (1) Only in the UI. Pro: small. Con: the API, database and scorer would still accept them. (2) In the contract validator for every v2 document. Pro: every module that validates gets the protection. Con: a real need for these characters (right-to-left scripts) would be blocked; Kannada and English never need them. (3) Also force it on v1. Con: changes v1 behaviour while other agents rely on it.
- What we chose: Option 2, plus an OPT-IN function for v1 (`bidi_errors(doc)` or `validate_doc(..., reject_bidi=True)`) so m5 and m6 can use it now.
- Why: Our text is Kannada and English only, so these characters have no honest use; blocking them in one shared place is cheap and closes a display trick.
- What we actually did: contracts/validate.py (`BIDI_CONTROLS`, `bidi_errors`, always on for record.v2 and gold.v2); attack fixtures fixtures/record.v2/invalid/bidi_override_in_advice_text.json, bidi_isolate_in_drug.json and fixtures/gold.v2/invalid/bidi_isolate_in_turn_text.json (written as \u escapes so the files themselves display honestly); 11 bidi tests.
- What could go wrong / weaknesses: Other invisible characters (U+200E/U+200F direction marks, U+061C) are NOT blocked because they were not in the finding; they cannot reorder text the same way but can still confuse. The UI must still escape text (XSS is a separate issue).
- What else could be done: block all Unicode "format" characters except ZWJ/ZWNJ, after checking that no Kannada text needs them.
- How to change this decision later: `BIDI_CONTROLS` in contracts/validate.py (with a CHANGELOG entry).
- Status: done (v2); opt-in for v1 (m5/m6 must call it)

### D-?: Small additions and conventions in record.v2 (injection without IV/IM, speaker roles, strength versus dose, age bands)   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: The requested lists left a few real cases with no honest value, and some fields need a writing convention so m1, m3 and the scorer fill them the same way.
- Options we considered: (1) Use only the requested values and squeeze other cases into "other" or "unknown". Pro: exactly as asked. Con: "injection" said without IV/IM would become "unknown" and lose the fact that it is not oral; a nurse or ASHA would be recorded as "doctor" or "unknown". (2) Add a few clearly named values and document them. Pro: honest records. Con: a slightly longer list to learn.
- What we chose: Option 2. Route adds `injection_unspecified`. Speaker adds `nurse`, `asha`, `pharmacist` (gold role "physician" maps to "doctor"). Conventions: dose = amount per time given (5 ml, 1 tablet, 500 mg, as in v1); strength = product strength only when said as such (120 mg/5 ml, or "500 mg, two tablets"); route null when not said even if a syrup implies oral; age bands infant < 1 y, child 1-9 y, adolescent 10-17 y, adult 18-64 y, older_adult >= 65 y; "ಮಗು" without an age = child.
- Why: The verifier can only flag what the record can express. Keeping dose with its v1 meaning keeps old scores comparable.
- What we actually did: enums and descriptions in both v2 schemas; conventions in contracts/README.md; fixture rec2-fx-inj-008 uses injection_unspecified.
- What could go wrong / weaknesses: The age-band cut-offs are an architect choice, UNVERIFIED (no source fetched). "ಮಗು = child" may hide an infant. Whether "500 mg tablet" should also fill strength is a judgement call for a clinician.
- What else could be done: take age bands from a fetched WHO or national guideline; ask a pharmacist about strength versus dose.
- How to change this decision later: new schema version plus contracts/README.md conventions.
- Status: needs human (age bands and strength convention to confirm)

### D-?: A careful converter from v1 to v2, and the order in which modules move   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: Existing v1 records and gold files must keep working while modules move to v2 one by one. How do we convert them, and what should the converter guess?
- Options we considered: (1) Guess new fields from v1 (for example negated -> "advised_against", syrup -> oral). Pro: richer converted data. Con: a guess becomes a clinical claim nobody made. (2) Convert conservatively: new fields null, status "unknown", speaker "unknown" for records (transcripts have no speaker roles), speaker from the turn role for gold (that is exact). Pro: never invents. Con: converted data cannot measure the new classes.
- What we chose: Option 2, with a check that the input is valid v1 and the output valid v2 (it refuses otherwise).
- Why: A converter that guesses would hide exactly the errors v2 is meant to expose.
- What we actually did: contracts/migrate_v1_to_v2.py (`migrate_record`, `migrate_gold`, CLI `uv run python -m contracts.migrate_v1_to_v2 record in.jsonl -o out.jsonl`); 5 tests; one migrated fixture. Migration order in contracts/README.md: m3 extract, m4 checks (C4 route/paediatric/liquid strength), m5 DB columns, m6 display, m7 scorer severity mapping, m1 gold.v2.
- What could go wrong / weaknesses: Converted records look complete but carry no route/strength/age; reports must say "not measurable" for them (written into docs/severity.md).
- What else could be done: re-extract with m3 instead of converting once m3 emits v2.
- How to change this decision later: contracts/migrate_v1_to_v2.py and its tests in tests/test_record_v2.py.
- Status: done (tool); module migration not done

### D-?: Landing a contract change while another agent runs the full test suite   (Phase C / contracts / architect / 2026-11-12)
- What we needed to decide: An audio agent was running the whole test suite while this change was made. Three things could break it: (a) a test said "exactly eight schemas"; (b) the fixture script deleted and rewrote every fixtures folder, so a test reading fixtures at that moment could fail; (c) the m3 "no test-only words" guard counts every fixture word as dev-visible, so a new fixture word that appears only in test templates would quietly weaken it.
- Options we considered: (1) Edit files in place. Con: half-finished states visible to the other agent. (2) Build and test everything in a private copy, then copy in, in a safe order (validator and fixtures before schemas, new test last).
- What we chose: Option 2, plus: the "eight schemas" test now accepts numbered later versions (it still requires all eight v1); the fixture script writes only changed files and never deletes a folder; every new Kannada fixture word was checked against the test-only word list (none were test-only).
- Why: "Nothing existing may break" includes the moment of the change, not only the end state.
- What we actually did: tests/test_contracts.py (one test loosened, still strict on v1), fixtures/build_fixtures.py (`sync_dir`, re-run reports "files changed: 0"); v1 fixture files are byte-identical (checked with diff).
- What could go wrong / weaknesses: The full suite had one collection error in the audio agent's unfinished m1_data/tests/test_audio_build.py (module not written yet); that is theirs, not caused by this change.
- What else could be done: a CI step that fails if build_fixtures.py would change any committed fixture.
- How to change this decision later: fixtures/build_fixtures.py, tests/test_contracts.py.
- Status: done
