# Decisions explained (MaatuMitra)

## What this project is

1. MaatuMitra is a class experiment for a course on antimicrobial resistance (AMR).
2. It is a "voice scribe": someone speaks Kannada, the computer writes it down.
3. Then a program turns the words into a structured record: symptoms, medicines, doses, advice.
4. Every item in the record must point to the exact words that were spoken (its "evidence").
5. A separate safety checker looks for dangerous mistakes, like a lost "not" or a wrong dose.
6. A human must approve the record before it counts as "saved". Nothing is saved automatically.
7. Different roles (ASHA worker, nurse, doctor, pharmacist, researcher) see only what they need.
8. A small helper answers questions about antibiotics only from approved cards, or says "ask a doctor".
9. All data is fake (synthetic). It is NOT a clinical tool and must never be used on real patients.
10. The goal is an honest, repeatable experiment that shows what works AND where it fails.

## How to read this file

- Each decision has an ID like D-7. The index table below lists all of them with a one-line outcome.
- Entries are in the order they happened. Old entries are never deleted; a changed decision gets a new entry that points to the old one.
- Every entry uses the same headings: what we had to decide, the options, what we chose, why, what we did, what could go wrong, what else could be done, how to change it, and its status.
- Words in **bold** the first time are explained in docs/glossary.md.
- "UNVERIFIED" means nobody has checked it yet. "Not native-validated" means no native Kannada speaker has checked it.
- Builder agents do not edit this file directly: they write `<module>/handoff/decisions.md`, which is merged here (see D-8).

### D-1: Check the laptop before building   (Phase A / architect / architect / 2026-11-09)

### D-2: Python environment: uv, a lockfile, light base + optional heavy extras   (Phase A / architect / architect / 2026-11-09)
- What we needed to decide: How to install Python packages so that anyone gets exactly the same versions, without filling the small disk.
- Options we considered:
  1. Plain `pip install -r requirements.txt` without exact versions. Pro: familiar. Con: versions drift; results may not repeat.
  2. pip-tools (a **lockfile** made by pip-compile). Pro: exact versions. Con: an extra tool; slower.
  3. **uv** with `pyproject.toml` + `uv.lock`. Pro: exact versions for every package, very fast, already installed. Con: one more tool for students to learn.
  4. Install everything (including PyTorch and speech models) by default. Pro: one command. Con: several GB; the laptop has ~11 GB free.
- What we chose: Option 3, with heavy packages as **optional extras**: `asr` (faster-whisper, soundfile, librosa, jiwer, papermill, ipykernel), `tts` (soundfile, librosa; m1 adds its engine), `llm` (ollama client), `helper` (sentence-transformers). Base = pytest, jsonschema, regex, pyyaml, ruff, numpy, pandas, matplotlib, fastapi, uvicorn, pydantic, psycopg[binary], pyjwt, streamlit, httpx, pre-commit, pip-audit.
- Why: The lockfile makes runs repeatable; extras keep `make setup` small (~400 MB). A module that needs speech models installs them with `uv sync --extra asr`.
- What we actually did: pyproject.toml, uv.lock (179 packages resolved), .python-version (3.11). `make setup` runs `uv sync --locked`. Python 3.11.15 (uv-managed).
- What could go wrong / weaknesses: The lock also pins the extras; their install on Windows/CPU/GPU is UNVERIFIED until m2/m8 try. PyTorch wheels are large.
- What else could be done: Add a CUDA-specific index for PyTorch if m2 needs GPU wheels (a decision entry by m2).
- How to change this decision later: Edit `[project.dependencies]` or `[project.optional-dependencies]` in pyproject.toml, then `uv lock`. Modules ask via their handoff notes.
- Status: done

### D-3: Problem: Windows path-length limit broke the environment   (Phase A / architect / architect / 2026-11-09)
- What we needed to decide: Where to keep the Python environment (the **venv**) on this laptop.
- Options we considered:
  1. `.venv` inside the repo (uv default). Pro: standard. Con: the repo path is ~180 characters; with package paths it passes Windows' 260-character limit (**MAX_PATH**). It really failed: jsonschema could not open one of its files.
  2. Turn on Windows long paths. Pro: fixes it for everything. Con: a system setting change; agents must not change system settings; needs the human.
  3. Keep the venv at a short path, `%USERPROFILE%/.venvs/maatumitra`, using the `UV_PROJECT_ENVIRONMENT` variable. Pro: works now, no system change. Con: one extra variable; two clones on one Windows machine share one venv unless the variable is set.
- What we chose: Option 3, done automatically by the Makefile on Windows (only if the user has not set the variable). Linux/CI keep `.venv`.
- Why: It works without touching system settings.
- What we actually did: Makefile block `ifeq ($(OS),Windows_NT)`. README explains: when calling `uv run` directly on Windows, first `export UV_PROJECT_ENVIRONMENT=$USERPROFILE/.venvs/maatumitra`. Second small problem: `uv python install 3.11` failed with "Missing expected target directory for Python minor version link" (uv 0.12.1 here); we created the venv by pointing uv at the managed Python 3.11.15 interpreter file directly.
- What could go wrong / weaknesses: If someone runs `uv run` on Windows without the variable from a long path, it fails the same way. The uv bug cause is UNVERIFIED.
- What else could be done: The human may enable long paths (HUMAN_TODO) or clone the repo to a short path like C:\mm.
- How to change this decision later: Remove the Windows block in the Makefile.
- Status: done

### D-4: No Docker: how m5 will get PostgreSQL 16   (Phase A / architect / architect / 2026-11-09)
- What we needed to decide: The brief wants PostgreSQL 16 in Docker, but this laptop has no Docker and no Postgres.
- Options we considered:
  1. Install Docker Desktop. Pro: matches the brief. Con: big download, needs admin rights and the human; uses scarce disk.
  2. Use MariaDB, which is installed. Pro: zero setup. Con: it is NOT Postgres: no row-level security (**RLS**) like Postgres; the security design would not hold.
  3. An embedded pip package that ships a Postgres server (for example `pgserver`). Pro: `uv add` and go. Con: which Postgres version and licence are UNVERIFIED.
  4. Official portable Postgres 16 binaries (EnterpriseDB zip). Pro: real Postgres 16. Con: manual download; licence and size UNVERIFIED.
- What we chose: Keep `docker-compose.yml` (postgres:16.15 pinned by digest, port 127.0.0.1:5432 only) for people with Docker; m5 must pick option 3 or 4 after verifying it, and record a decision.
- Why: The security design needs real Postgres 16 features. The architect only checked that `pgserver` exists on PyPI (version 0.1.4); the rest is m5's job.
- What we actually did: docker-compose.yml; infra/inventory.md section 3. `postgresql-wheel` was also seen on PyPI but its version 14.1.2 means Postgres 14, so it does not fit.
- What could go wrong / weaknesses: pgserver may bundle another Postgres version or not work on Windows (UNVERIFIED). The compose file has never been run here.
- What else could be done: Run the m5 tests in CI on Linux with a Postgres service container.
- How to change this decision later: m5 writes a new decision; edit docker-compose.yml and m5_backend.
- Status: partly done

### D-5: One Makefile that works with make and mingw32-make   (Phase A / architect / architect / 2026-11-09)
- What we needed to decide: How to give one set of commands (`make test`, `make eval`, ...) on Linux CI and on this Windows laptop, which only has `mingw32-make`.
- Options we considered:
  1. A Python task runner (for example a tasks.py). Pro: same everywhere. Con: the brief asks for `make` targets.
  2. A Makefile with Windows-only commands. Pro: works here. Con: breaks CI.
  3. One GNU Makefile with `SHELL := bash` and plain bash commands. Pro: same file on Linux and Windows (run from **Git Bash**). Con: Windows users must use Git Bash and type `mingw32-make`.
- What we chose: Option 3. Every target calls `uv run ...`. Each module has `module.mk` with `mN-test` and `mN-mock`; the root includes all eight. Modules add themselves to `make data / eval / eval-full / eval-test / demo / clean` by appending to variables like `EVAL_TARGETS += m7-eval`.
- Why: The root Makefile never needs editing when a module grows, so parallel builders do not conflict on it.
- What we actually did: Makefile, m1_data/module.mk ... m8_helper/module.mk. Checked here: `mingw32-make test`, `lint`, `validate-fixtures`, `split-lock`, `m4`, `data`, `eval-test` (refuses), `audit`.
- What could go wrong / weaknesses: Running mingw32-make from PowerShell may pick a different bash (for example WSL's) and fail; use Git Bash. CI behaviour UNVERIFIED until pushed.
- What else could be done: Add a `justfile` or tasks.py later if Windows users struggle.
- How to change this decision later: Makefile and */module.mk.
- Status: done

### D-6: Contracts as one shared, importable package with a validator   (Phase A / architect / architect / 2026-11-09)
- What we needed to decide: How modules agree on data formats while staying independent.
- Options we considered:
  1. Each module writes its own checker. Pro: full independence. Con: eight slightly different ideas of "valid".
  2. One `contracts/` package with the **JSON Schemas** and `validate.py`, importable by every module. Pro: one definition of "valid". Con: modules depend on it (but it is a contract, not module logic).
- What we chose: Option 2. JSON Schema **draft 2020-12** for structure, plus "semantic" rules a schema cannot express (NFC text, offsets that match the text, auto-accept only without flags, and others listed in contracts/CHANGELOG.md).
- Why: A wrong format found at the boundary is cheap; found at the end it is expensive.
- What we actually did: contracts/schemas/*.schema.json (8), contracts/validate.py, contracts/CHANGELOG.md. CLI: `uv run python -m contracts.validate <schema> <file.json|file.jsonl|dir>` and `--check-fixtures fixtures`. Tests: tests/test_contracts.py (46 tests).
- What could go wrong / weaknesses: Matching a record's evidence against its transcript needs both files, so `validate.py` alone cannot do it; m3, m4 and integration must. Some semantic rules are architect choices that a module may find too strict.
- What else could be done: Publish the validator as a small package if the project grows.
- How to change this decision later: A new schema version + CHANGELOG entry, approved by the architect (section 4).
- Status: done

### D-45: Fail-closed verifier with a rule registry   (Phase B / m4_verify / safety-engineer / 2026-11-09)
- What we needed to decide: How the safety checker should behave when something goes wrong inside it, and how to switch single checks off for the ablation experiment (E3).
- Options we considered: (1) Catch errors and ignore them: simple, but a crash would silently let a bad record through (unsafe). For switching checks off: (a) edit code, (b) a list of checks in a config file.
- What we chose: (3) plus (b). Every check is a plain function in `REGISTRY` (checks.py); the verifier calls it, and ANY exception becomes status "flag" with reason "check_error: ...". A record is "auto-acceptable" only if nothing flags AND at least one check actually passed.
- Why: "Fail-closed" means: when unsure, ask a human. A checker that says "fine" after crashing is the worst outcome. A config list (`disabled: [C3]`) lets E3 remove one check at a time without touching code.
- What we actually did: `m4_verify/verifier.py`, `m4_verify/checks.py`, `m4_verify/config/default.yaml`. Tests: `uv run pytest m4_verify/tests/test_checks.py -k "fail_closed or disable or garbage or malformed"` (forced exception in each of C1..C8 gives flag + check_error + auto_acceptable false).
- What could go wrong / weaknesses: A check that returns "pass" by mistake (a logic bug, not an exception) is not caught by this mechanism; only tests can find that. If ALL checks are disabled the record is never auto-acceptable (by design).
- What else could be done: Run two independent verifiers and require both to pass; property-based tests.
- How to change this decision later: `m4_verify/verifier.py` (the try/except and the auto_acceptable rule).

- Options we considered: (1) Read the shared table `.claude/skills/kannada-nlp/negation_table.yaml` (same as m3): a mistake in the table would then be invisible. (2) Hand-code our own rules from the brief and grammar knowledge: independent. (3) A statistical model: needs labelled Kannada data we do not have.
- What we chose: (2). Whole-word cues (ಇಲ್ಲ, ಇಲ್ಲಾ, ಅಲ್ಲ, ಬೇಡ, ಬೇಡಿ, ಬಾರದು, ಕೂಡದು), token-final suffixes (-ಿಲ್ಲ, -ುದಿಲ್ಲ, consonant+ದಿದ್ದರೆ, fused -ಬಾರದು/-ಕೂಡದು/-ಬೇಡ(ಿ)), -ದೆ only on a verb-stem list, soft casual -ಲ್ಲ, ಯಾವುದೇ...ಇಲ್ಲ, English no/not/never. Scope = the clause (split at punctuation and ಆದರೆ/ಮತ್ತು/ಹಾಗೂ/ಆದ್ದರಿಂದ). Cross-turn: a turn whose FIRST clause is only ಇಲ್ಲ/ಇಲ್ಲಾ/ಹೌದು answers the previous turn's question clause(s). Soft cues count as negation (conservative) and also raise C8.
- Why: Matching on whole tokens (never substrings) avoids the classic trap ಇಲ್ಲಿ (here) containing ಇಲ್ಲ. "First clause" (not "whole turn") was chosen because answers like "ಇಲ್ಲ, ಅವನು ಮಲಗಿದ್ದ." are common; this is a documented extension of the brief.
- What we actually did: `negation.py`; 125+ tests in `tests/test_negation.py` (every cue: positive, minimal-pair twin, trap; clause scope; cross-turn); audit in `negation_audit.md`.
- What could go wrong / weaknesses: Not native-validated. Coordination ("A ಮತ್ತು B ಬೇಡ") is handled by a heuristic (bare item inherits the negation and C8 flags it). Questions without "?" (ASR text often has no punctuation) are not recognised as questions. Double negation fused with quotatives is missed (audit line 40).
- What else could be done: Native-speaker review of every rule; a held-out real-text audit; real spoken transcripts.
- How to change this decision later: `negation.py` (rule tables at the top) and its tests.
- Status: partly done (rules are hypotheses; needs human)
