### D-?: The verifier only reads dev data, checked by a list of allowed ids, not by folder names   (Phase B / m4_verify / safety-engineer / 2026-11-11)
- What we needed to decide: How m4 makes sure its planted-mistake experiment (E4) and its confidence-threshold tuning (tune-c7) never read the frozen TEST split. The old guard (M4-1, CRITICAL in the integrity review) refused a path only if its name contained the word "test". But the test gold files sit in the same folder as the dev files (data/gold/), so `e4 --gold-dir data/gold` would have read all 264 test files.
- Options we considered:
  1. Keep the name check and tell people not to point it at data/gold. Pro: no work. Con: one wrong command leaks the test split; a copied folder with a harmless name passes.
  2. A deny-list: refuse ids in data/splits/test.txt. Pro: simple. Con: a file whose id was changed slips through; under data/ we would still open the test files to read their ids.
  3. An allow-list plus several deny checks: under data/ open a file ONLY if its id is in data/splits/dev.txt; everywhere refuse a document whose id is in test.txt, whose template family is a test family (data/splits/split_plan.json), or whose bytes match a hash in data/splits/test.lock. Pro: test files under data/ are never even opened; copies and renamed files are caught. Con: a test document that was both re-labelled AND edited would still pass (no check can catch everything).
- What we chose: Option 3.
- Why: The test split is the only honest final exam we have. A guard that fails open on one wrong command is not a guard. Checking the id, the family and the file hash costs almost nothing.
- What we actually did: New file m4_verify/split_guard.py (load_gold, read_guarded_json, guard_doc, guard_bytes). planted.load_gold_dir and tune_c7.main now go through it; the old name check (refuse_test_split) is deleted. The CLI prints "error: REFUSED: ..." and exits with code 2. The only way past is ALLOW_TEST=1 together with a non-empty PURPOSE=...; every such read is appended to results/m4_verify/test_access_log.md. Nobody set ALLOW_TEST in this work. Tests: m4_verify/tests/test_split_guard.py (15 tests: data/gold gives exactly the 328 dev ids and no test file is opened; a copied folder, a renamed file, a test family under a new id, a JSONL dump and a hash-identical copy are all refused; missing split lists fail closed; tune-c7 refuses a test transcript by audio id and by data path without opening it; the CLI refuses). These tests never read test content: the "test documents" are fixture files with a test id written into them. Run: `uv run pytest m4_verify/tests/test_split_guard.py -q`.
- What could go wrong / weaknesses: A test conversation that is copied, given a new id, moved to a dev family name AND edited by one character would pass. The audit log is m4's own (results/m4_verify/test_access_log.md), not the project log results/test_access_log.md that `make eval-test` writes (m4 may not write outside its folders); see open_questions.md. The `verify` command (one record at a time, used by the app) is not guarded, on purpose: it is not a tuning or evaluation reader.
- What else could be done: Move the guard into a shared helper that every module uses (needs an orchestrator decision, since modules may not import each other); add a CI test that runs every m4 command on data/ and checks the access log stays empty.
- How to change this decision later: m4_verify/split_guard.py and m4_verify/tests/test_split_guard.py.
- Status: done

### D-?: The dose check (C4) never passes a child's dose, and says "cannot verify" apart from "wrong"   (Phase B / m4_verify / safety-engineer / 2026-11-11)
- What we needed to decide: The simulated clinical review (reviews/m4_verify/2026-11-10-clinical.md, ai_simulated_review, accepted in D-91) found that C4 compared every dose with the ADULT range, so "paracetamol 500 mg for a child" passed; that "no range in our drug list" looked the same as "dose is wrong"; that every unit (ml, sachet, tablet) was allowed for every drug ("ceftriaxone 1 tablet" or "ORS 500 mg" passed the unit test); and that the maximum daily dose was used only where the drug list has it.
- Options we considered:
  1. Add a children's dose table. Pro: could really check child doses. Con: we have no fetched paediatric source (IAP / NLEM not fetched); inventing doses is forbidden.
  2. Flag every dose in a conversation that mentions a child as "cannot verify" (fail-closed), and split C4 reasons into codes. Pro: safe, honest, cheap. Con: more flags for humans to review; it cannot tell a correct child dose from a wrong one.
  3. Keep one flag type and only fix the child case. Pro: less work. Con: scores would keep mixing gaps in our drug list with real dose errors (alarm fatigue).
- What we chose: Option 2, plus allowed units per drug and the existing max-daily check with its own code.
- Why: A verifier must never certify what it cannot check. Separating "cannot verify" from "wrong" keeps the measurement honest: the scores now show how much review burden comes from our own lexicon gaps.
- What we actually did: m4_verify/checks.py C4: every flag reason now starts with a code and a severity class from docs/severity.md, e.g. `cannot_verify:paediatric [CR-PAEDIATRIC]: ...`. Codes: real violations `span_mismatch`, `unit_not_allowed` (CR-ROUTE for an injection-only drug given as tablet/ml, else CR-DOSE), `out_of_range`, `exceeds_max_daily`; cannot-verify `cannot_verify:paediatric` (a child word such as ಮಗು/ಮಗುವಿಗೆ/ಮಕ್ಕಳ/ಶಿಶು or "child" anywhere in the conversation), `cannot_verify:no_range` (blank range), `cannot_verify:not_in_lexicon`, `cannot_verify:liquid_strength` (dose in ml: no mg-per-5 ml strength known, CR-LIQUID-STRENGTH), `cannot_verify:count_unit` (tablets/capsules: strength not stated). Allowed units: m4 config table m4_verify/config/default.yaml (paracetamol adds ml for syrup; iron-folic acid tablet/mg/mcg; ORS sachet/ml) -> else the dosage form named in the lexicon's verified_by note (tablet, capsule, syrup, sachet, powder for injection: m4_verify/lexicon.py units_from_note) -> else solid oral forms only (mg, g, mcg, tablet, capsule). Max daily uses only data/lexicon/drugs.csv values (paracetamol 4000, ibuprofen 3200, metformin 2550 ...). Tests: m4_verify/tests/test_c4_fixpass.py (written first; before the fix the child 500 mg dose PASSED C4). Helpers `reason_code()` and `severity_class()` let reports count the codes.
- What could go wrong / weaknesses: The child word list is AI-written and not native-validated; ಮಗ/ಮಗಳು (son/daughter) are NOT cues because adults are often called that, so a child named only that way is missed. Any child word anywhere flags ALL doses in the conversation (for example an adult's own dose in a visit about a child). Units derived from free-text notes can be wrong if a note mentions a form in passing (amoxicillin-clavulanate gets ml because its note mentions a suspension label). The paracetamol syrup row is UNVERIFIED (no syrup strength fetched). Review burden on error-free dev records goes up; that is shown in the results, not hidden.
- What else could be done: Add age/weight and route fields to record.v2 (contract change), a fetched paediatric dose table, and a unit column in drugs.csv.
- How to change this decision later: m4_verify/checks.py (c4_dose_range), m4_verify/lexicon.py (CHILD_PREFIXES_KN, units_from_note), m4_verify/config/default.yaml (allowed_units, allowed_units_by_drug), and the tests in m4_verify/tests/test_c4_fixpass.py.
- Status: done (clinical values need human check)

### D-?: Planted drug swaps use only look-alike drugs from our drug list   (Phase B / m4_verify / safety-engineer / 2026-11-11)
- What we needed to decide: How the planted-mistake generator (E4, type f "drug swap") picks the wrong drug. Before, it could pick a look-alike that is not in our drug list (prednisone, fomepizole, sertraline...), which C2/C4 then caught trivially as "unknown drug", or fall back to a RANDOM drug when no look-alike was listed (clinical review M4-M4).
- Options we considered:
  1. Keep the random fallback. Pro: more swaps. Con: "paracetamol -> metformin" is not a realistic confusion and is easy to catch; it inflates the catch rate.
  2. Only use look-alike pairs from the confusable_with column of data/lexicon/drugs.csv, read in both directions, and only drugs that are in the list. Pro: realistic and honest. Con: drugs with no listed look-alike (paracetamol, ibuprofen, zinc ...) are never swapped.
  3. Add AI-proposed pairs (dexamethasone/prednisolone, diclofenac/ibuprofen). Pro: more coverage. Con: not from a fetched source.
- What we chose: Option 2.
- Why: A planted mistake should look like a real one. Swapping to a drug the verifier does not know measures the drug list, not the verifier.
- What we actually did: m4_verify/planted.py: new `confusables(drug, lex)` (both directions, lexicon drugs only); `_swap_drug` has no fallback; medications whose drug has no confusable are not candidates. The E4 summary reports how many medication items can never be swapped. Test: m4_verify/tests/test_planted.py::test_drug_swaps_pick_only_lexicon_confusables (red before the fix, for both lexicons).
- What could go wrong / weaknesses: The confusable pairs in drugs.csv are mostly AI-proposed name-similarity pairs (UNVERIFIED; the ISMP list could not be read). Paracetamol, the most common drug in our data, is never swapped.
- What else could be done: Fetch a real confusable-names list (ISMP or an Indian source) and add the pairs to drugs.csv through m1.
- How to change this decision later: m4_verify/planted.py (confusables, _swap_drug) and data/lexicon/drugs.csv (confusable_with, via m1).
- Status: done

### D-?: Negation rules: spoken "don't", polite "no", negative questions, clauses without commas, abbreviations   (Phase B / m4_verify / safety-engineer / 2026-11-11)
- What we needed to decide: Which of the simulated Kannada reviewer's findings (reviews/m4_verify/2026-11-10-kannada.md, ai_simulated_review, accepted in D-93) to build into m4's OWN negation rules. m4 must not read the shared table .claude/skills/kannada-nlp/negation_table.yaml (independence).
- Options we considered:
  1. Copy the shared table's new version. Pro: one set of rules. Con: a mistake in the table would then be invisible to the verifier (both sides wrong in the same way); not allowed by the brief.
  2. Hand-code each accepted finding in m4_verify/negation.py with a positive sentence, a minimal-pair twin and a trap, written as failing tests first. Pro: independent and testable. Con: AI-written rules, not native-validated.
- What we chose: Option 2.
- Why: Missing "ತಗೋಬೇಡಿ" ("don't take") or reading "ಜ್ವರ ಇದೆ ಕೆಮ್ಮು ಇಲ್ಲ" ("fever yes, cough no") as "no fever" are safety bugs whatever their source.
- What we actually did: m4_verify/negation.py: (j) ಬೇಡ/ಬೇಡಿ/ಬೇಡಾ fused after any letter or sign (ತಗೋಬೇಡಿ, ಕೊಡ್ಬೇಡಿ, ತಿನ್ಬೇಡ; spaced ಕೊಡ ಬೇಡಿ already worked); (k) whole words ಬೇಡಾ, ಇಲ್ರೀ, ಇಲ್ರಿ, ಇಲ್ಲರೀ, ಇಲ್ಲಪ್ಪ, ಇಲ್ಲಮ್ಮ, and ಬೇಡವಾ/ಬೇಡವೇ/ಬೇಡ್ವಾ as negative questions; (l) new soft rule S-LVA for C+ಲ್ವಾ ("won't you ...?"): counted as negation but always flagged by C8 as "polarity uncertain" (ಅಲ್ವಾ, the tag "right?", still never triggers); (m) a clause also ends after a finite predicate (ಇದೆ, ಇಲ್ಲ, -ಿದೆ, -ಿಲ್ಲ) when more words follow without punctuation, except before a quotative (ಅಂತ, ಎಂದು), a tag (ಅಲ್ವಾ) or an address word; (n) a cross-turn answer may be one answer word plus address words ("ಇಲ್ಲ ಅಕ್ಕ", "ಹೌದು ಸರ್", "ಹೌದ್ರೀ"); (o) no clause split at the dot of an abbreviation (ಎಂ.ಜಿ., ಓ.ಆರ್.ಎಸ್., ಡಾ.). Tests: m4_verify/tests/test_negation_fixpass.py (61 tests; 28 failed before the fix: j 4, k 4, l 4, m 4, n 10, o 2). All older negation tests and every trap still pass (zero false triggers). The re-run of the real-text audit (m4_verify/negation_audit.md, last section) gives identical cue output on all 52 Wikipedia sentences.
- What could go wrong / weaknesses: Not native-validated. The new forms are tested only on AI-written sentences; the real-text audit contains none of them. "-ಬೇಡಿ" fused could also match ಕೈಬೇಡಿ (handcuffs), a rare word. Splitting after ಇದೆ could cut a clause that a native speaker reads as one. Not splitting after an abbreviation dot can merge two real sentences (for example "... 500 mg. ಕೆಮ್ಮು ಇಲ್ಲ."), which makes the dose look negated: this errs on the side of a false flag, not a missed negation. The reviewer's other low-confidence items (ಇಲ್ಲವಾದರೆ, ನಿಲ್ಲಿಸದೆ as positive, ಬಿಲ್ಲವ trap, more clause words) are not done.
- What else could be done: A real Kannada speaker fills reviews/human_sheets/negation_rules_review_sheet.csv; test on transcribed real speech.
- How to change this decision later: m4_verify/negation.py together with m4_verify/tests/test_negation_fixpass.py and test_negation.py.
- Status: done (needs human Kannada review)

### D-?: Honest E4 numbers: a catch must land on the planted field, counts use unique mutations with Wilson intervals, review burden sits next to recall, the second-transcript row is an upper bound   (Phase B / m4_verify / safety-engineer / 2026-11-11)
- What we needed to decide: How the planted-mistake experiment (E4) counts and reports results. The simulated integrity review (reviews/m4_verify/2026-11-10-integrity.md, ai_simulated_review, accepted in D-90) found four overclaims: (a) "caught" meant ANY flag anywhere in the record (5 of 30 wrong-patient "catches" were an unrelated paracetamol flag); (b) the README quoted repeated injections ("200/200") instead of unique mutations (for example 4/4, CI 0.51-1.0); (c) the review burden quoted used the friendly fixture lexicon (0/18) instead of the project lexicon (1/18); (d) the "second transcript" condition used the perfect gold text without saying so.
- Options we considered:
  1. Keep "any flag" and add footnotes. Pro: no code change. Con: a noisy verifier would look better; footnotes get lost.
  2. Field-level attribution plus unique counts as the headline, with the review burden on the SAME records printed next to every recall number, and the oracle row renamed. Pro: honest and checkable. Con: smaller-looking numbers and more columns.
- What we chose: Option 2.
- Why: A safety number that can be inflated by unrelated alarms or by repeating the same mutation is not a measurement. Recall without the false-alarm rate on clean records says nothing.
- What we actually did: m4_verify/evaluate.py: `caught` = a flag on the injected field, its item (item-level C7/C8 flag), the other half of the dose pair, or a max-daily flag; record-level "/" flags and other items never count. `detected` = the same but the flag is not cannot_verify and was not already present on the error-free record. `sent_to_review` = any flag (kept only as a secondary column). Every proportion is over UNIQUE mutations with a Wilson 95% interval (hand-checked values in m4_verify/tests/test_evaluate.py); repeats are listed as `n_injections`. New tables per_field.csv and a per_check.csv over unique mutations. The second-transcript condition is now called `oracle_second_transcript_upper_bound` everywhere. C7 now also flags the item whose clause holds a difference (before, only "/"), so field-level credit is possible. E4 was run on m1 DEV gold for the first time (data/gold filtered by dev.txt; 328 conversations; seed 20261109; 1800 record-level and 1600 transcript-level injections; 5528 verdicts, 0 schema errors). Dev results (results/m4_verify/dev/e4/summary.md): review burden on the same error-free records: 271/1200 fields flagged [0.203, 0.250], of which only 63/1200 [0.041, 0.067] are not "cannot verify" (the rest are mostly tablet counts, child doses and blank ranges); record level with encounter index, every type caught at the field, e.g. negation drop 193/193 [0.981, 1.0], digit change 200/200 [0.981, 1.0], digit swap 139/139 [0.973, 1.0], drug swap 185/185 [0.980, 1.0], wrong patient 200/200 [0.981, 1.0] (0/200 [0, 0.019] without the index); transcript level text-only: negation drop 14/193 [0.044, 0.118], drug swap 0/183 [0, 0.021], frequency 0/200, duration 0/200 [0, 0.019]; with the ORACLE second transcript (upper bound only) every unique mutation of all eight types is caught at the field (e.g. negation drop 193/193 [0.981, 1.0]). The fixture results (results/m4_verify/e4 and data_lexicon/e4) were regenerated with the same code.
- What could go wrong / weaknesses: Planted errors on synthetic, template-generated text are much easier than real mistakes; record-level 100% says the rules can see a value that disagrees with its own span, not that real extractor errors will be caught. The "dev" gold was generated by m1 from templates that m4's vocabulary was partly written against. The oracle row is an upper bound only; C7 with a real second ASR output (with its own errors) is not measured. Remaining clean-record flags come from verifier vocabulary gaps (symptom names chills / tiredness / breathing difficulty and the fused spelling ಮೈಕೈನೋವು are not in m4's symptom list) and from soft negation (ಇಲ್ಲದೆ) and unanswered questions; these are deliberately NOT fitted to the dev labels in this pass. One small vocabulary fix was made after the first dev run: the colloquial ದಿವಸ ("day") was missing from the duration words (the Kannada review had assumed it was there); this halved the non-cannot_verify clean flags (124 -> 63 of 1200 fields) and is disclosed as dev-informed.
- What else could be done: Natural-error evaluation on m3 output (kept separate from planted errors); a real second ASR transcript for C7; add the missing symptom names through a documented, dev-only vocabulary decision.
- How to change this decision later: m4_verify/evaluate.py (at_field, unique_outcomes, run_e4, _summary_md) and m4_verify/tests/test_evaluate.py; re-run with `mingw32-make m4-e4-dev`.
- Status: done
