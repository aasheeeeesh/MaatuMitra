# Security review: m6_ui (2026-11-11)

- Reviewer: security-auditor (AI agent). Label: **ai_simulated_review**. This is not a human or professional penetration test.
- Target: commit 2f2fcfe (clean tree), m6_ui on Streamlit 1.67.0 and httpx 0.28.1, Python 3.11. All data is synthetic.
- Method: I read app.py, highlight.py, gate.py, i18n.py, data.py, verifier.py, review.py, .streamlit/config.toml and module.mk, plus m5 `app/main.py` (only the endpoints m6 calls). I ran 31 concrete attempts: 17 Streamlit AppTest attacks (MODE=mock), 10 HTTP and socket probes against two short local server runs, 3 secret scans and pip-audit. The scripts and raw logs are in my scratchpad (`m6sec/attack_apptest.py`, `attack2.py`, `apptest*.jsonl`); they are not in the repo.
- What I did NOT run: live mode (`MODE=live`) against a real m5 API and database. I did not start the m5 database. Everything about live mode is from code reading and is marked UNVERIFIED. gitleaks is **not installed**, so I ran a regex scan plus an exact-match scan for the `.env` secret values instead. I did not open a real browser, so how the browser renders things (markdown in button labels, iframes) is UNVERIFIED.
- Known and NOT re-reported: m6 still sends the old `/save` body `{verdict}`, but m5 now wants `{verdict_id, resolutions}`. This is scheduled for Phase C. See "Naive adaptation" below.
- Both servers I started were stopped (no listener left on 8501 or 8599). No database was started.
- Baseline: `MODE=mock uv run pytest m6_ui/tests -q` gave 105 passed.

## Findings (severity words from docs/severity.md: critical / major / minor)

### F1 (major): the role is chosen by a click, so any role can see every patient and approve
- Where: `app.py` `_role_picker`, `_nav`, `_page_record`, `_page_review`, `_approve`. `ss.role` only changes the text "You are: ...". No screen, row, button or gate call checks the role.
- Demonstrated (mock):
  - RC-1: as **pharmacist**, I opened `rec-fx-asha-001` and clicked Approve. Result: `(True, 'saved')`.
  - RC-2 / RC-2b: as **ASHA**, the record picker lists all 8 records of 7 different patients. I opened `rec-fx-pharm-003-asr` (a pharmacy patient) and its transcript was shown.
  - RC-3: "Change role" goes nurse -> ASHA with no password, and the Approve button stays enabled.
- Live mode (code reading, UNVERIFIED): `HttpGate` logs in once with the single server-side credential `M6_API_USER`/`M6_API_PASSWORD`. That means every browser user, in every role, calls m5 as that one user. m5's RLS, its physician-only `/save` and its audit log all see that one identity. Who actually clicked is lost. If that user is a physician, a pharmacist at the UI can save clinical records through it.
- Exploit scenario: a pharmacist (or anyone who can open the laptop's browser) picks "Doctor" or "Pharmacist" and approves a record. The audit log names the configured physician.
- Fix: in live mode, show a real login per person (m5 `/auth/token`), keep that person's token in their own session, and take the role from the token, never from a button. Hide or disable Approve unless the token role is physician. Load the record list from m5 (so RLS filters it) instead of the local catalogue. On role change, drop the token and the session state. Keep the click-to-pick role only in MODE=mock, clearly labelled.

### F2 (major): in live mode the screen shows a local file, but the server saves a different stored record
- Where: `data.Catalogue` always reads `fixtures/` and `m6_ui/fixtures/`, also in live mode. `HttpGate._post` maps the local `record_id` to an m5 UUID through the `M6_SERVER_IDS` JSON file. m6 never calls `GET /records/{id}` or `POST /records/{id}/verify`.
- Effect (code reading, UNVERIFIED live): the physician reviews the local fixture text, but approves whatever the m5 row with the mapped UUID contains. A wrong or tampered mapping file, or a server record that changed since the fixture was exported, means a human approves a record they never saw. This is the CR-PATIENT class (record attached to another patient). It also skips RLS for reading, as in F1.
- Fix (Phase C): fetch the record and the stored verdict from m5 (`GET /records/{id}`, `POST /records/{id}/verify`). Render exactly that JSON. Send that `verdict_id` back. Remove the id-mapping file.

### F3 (minor): the Approve-then-Save order leaves the server record "approved" when the save is refused
- Where: `app.py` `_approve` calls `gate.approve(rid)` and then `gate.save(...)`. `HttpGate.approve` calls m5 `POST /records/{id}/approve`, which (m5 `main.py` lines 311-316) sets `status='approved', approved_by, approved_at` with **no** flag check. If `/save` is then refused, m6 says "NOT saved", but the server row stays `approved` and is stamped with an approver.
- Mock evidence: G-2b shows the mock gate's status is `approved` after a refused save. The m5 behaviour is from code reading (UNVERIFIED live).
- Fix: in Phase C, call only `/save` (m5 D-94: save = approve). m5 should also consider removing `/approve`, or gating it the same way.

### F4 (minor): stale or double-submit state shows the wrong result, and saved records stay editable
- G-4: approve gives "saved". Approving again gives `error_other 'already saved'`, and the screen now shows the red "NOT saved" box, but the gate status is `saved`. A user may then retry or re-enter the record.
- G-5: after a save, the "No, change it" edit buttons are still offered. An edit then shows a record that differs from the saved one.
- Fix: when `gate.status(rid) == "saved"`, hide Approve and the edit buttons, and show the saved banner. Treat a repeat approve of a saved record as "already saved" (green), not as a refusal.

### F5 (minor, mock only): `M6_MOCK_GATE_REFUSE=1` can be switched off from the browser
- G-3: with the env variable set, unticking the demo checkbox and clicking Approve gave `(True, 'saved')`. The README says the variable "makes the mock server refuse every save".
- Fix: if the env variable is set, show the checkbox disabled (or do not render it) and never lower `force_refuse` below the env value.

### F6 (minor): Unicode bidi control characters pass the schema and are shown unchanged
- X-4: a `record.v1` with U+202E (right-to-left override) in `patient_ref` validates with 0 errors. `highlight.esc` keeps the character. In a field such as a dose or a patient reference, this can visually reorder the digits shown to the reviewer (for example "500" displayed differently). Browser rendering was not checked (UNVERIFIED).
- Fix: reject U+202A-202E and U+2066-2069 in record/transcript strings (contracts), or replace them with a visible marker before rendering. Keep ZWJ/ZWNJ (needed for Kannada).

### F7 (minor, mock only): the mock re-verifier passes an edited drug that is a single letter of the evidence
- G-6: in `rec-fx-asha-002`, editing the drug `paracetamol` to the single character `ಪ` gave `C2 pass`, so the mock gate would save it. The cause is the substring test `needle in span.casefold()` in `verifier.MockVerifier._recheck`. This is a documented stand-in, but demo videos and screenshots would show a meaningless drug as accepted.
- Fix: match whole tokens only, and require a minimum length or a drug-lexicon hit. Label mock saves as "saved (MOCK)".

### F8 (minor, low confidence, UNVERIFIED): no anti-framing headers
- `GET /` on 127.0.0.1:8501 returned no `X-Frame-Options` and no `Content-Security-Policy: frame-ancestors`. A page the user opens in the same browser could frame the app and trick a click (clickjacking) on the role buttons or Approve. Websocket hijacking from a foreign origin is blocked (Origin evil -> 403). I did not test whether the browser's private-network rules stop the iframe.
- Fix: the app has no auth, so live mode should sit behind a login (F1). Optionally, serve it through a local reverse proxy that adds `frame-ancestors 'none'`.

## Naive adaptation of `/save` (Phase C), code reading against m5 `save_record`
- Sending resolutions built from m6's local verdict (the client verifier) instead of the server's `/verify` `unresolved` list: m5 compares against its stored verdict and answers 422 or 409. This fails closed, so the gate cannot be bypassed.
- Sending `action: "edited"` without PATCHing the record and re-running `/verify` on the server: m5 answers 409 "edited record is not cleanly re-verified". This fails closed.
- m6 keys a flag by `check|path|reason`, but m5 keys by `(check_id, field_path)`. Two flags on the same path with the same check would produce duplicate resolutions, and m5 answers 422. This fails closed, but it is a usability bug.
- Real risks: F1 (a shared physician token makes any UI user a "physician"), F2 (the record shown is not the record saved), F3 (`/approve` first). A "confirm all" shortcut must never be added: m5 cannot tell a looked-at flag from a bulk click.
- `HttpGate` maps every 409 to `refused_unresolved_flags`, even "verdict is stale" or "already saved". This is misleading, but it fails closed.

## Read-only checks that held (code reading)
- XSS: every data string goes through `highlight.esc` (`html.escape(quote=True)`) before our own markup is added. Kannada and i18n text are escaped too. There is no `unsafe_allow_html`, no `components.html` and no `st.markdown` with data. `st.html` sanitises with DOMPurify by default and m6 never sets `unsafe_allow_javascript` (read in the installed Streamlit source, not fetched from a URL).
- Tokens: the bearer token lives only in the server-side `HttpGate` object in session state. It is sent only in the `Authorization` header and never appears in a URL, a log or the page. `API_URL` must be loopback. httpx does not follow redirects by default. `showErrorDetails="none"`. There are no `print`/`logging` calls on the app path. One weakness: the token is never refreshed, so after it expires every call returns `refused_auth` (this fails closed).
- Live verifier: a fixed argv list with no shell, a temp directory, and fail-closed on any error.
- Audio: m6 plays only the user's own upload (live) or a synthetic tone (mock). It never calls m5's audio endpoint, so there is no IDOR path. Uploads are filtered by extension only, with a 25 MB cap.
- XSRF protection on, CORS protection on, static serving limited to `static/` (font, CSS, OFL). The in-app bind guard treats `None` as safe. That is harmless here, because Streamlit 1.67 bound 127.0.0.1 even without the config file (B-2).

## Recommended decisions (for the orchestrator)
1. Accept F1 and F2 as Phase C blockers for live mode: per-user m5 login, role taken from the token, record and verdict loaded from m5, no id-mapping file.
2. Accept F3 with the `/save` adaptation (drop the `/approve` call).
3. Accept F4-F7 as small m6 fixes. F6 may need a contract change (request via open_questions).
4. Defer F8 (local-only demo); revisit if the app is ever served beyond one laptop.
5. Human: install gitleaks with a verified checksum and run `gitleaks detect` on tree and history (still never run in this project).
