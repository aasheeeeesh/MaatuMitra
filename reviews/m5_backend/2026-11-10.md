# Security review: m5_backend (2026-11-10)

- Reviewer: security-auditor (AI agent). Label: **ai_simulated_review**. This is not a human or professional penetration test.
- Target: commit c6fdf72 (m5_backend builder output). Database: local EDB PostgreSQL 16.15 on 127.0.0.1:54329. All data is synthetic.
- Method: I read the code (sql/, app/, scripts/, seed/, matrix/, tests/), ran the test suite, ran pip-audit and a regex secret scan, and made concrete break attempts against the local sandbox database and the FastAPI app (TestClient). Every attempt below gives the command, what should happen, and what actually happened.
- Scope limits: I did not look at the UI (m6), so XSS in the UI is checked only at the API boundary. gitleaks was **not run** because it is not installed and I am not allowed to download it without a checksum. A regex scan ran instead. Docker was not tested.

## Findings (severity per docs/severity.md wording: critical / major / minor)

### F1 (major): the save gate trusts a verdict that the client sends
- Where: `app/main.py` `save_record`. The body `{"verdict": ...}` comes from the client. The only binding is `verdict.record_id == records.json->>'record_id'`.
- Effect: a physician's client (or any script that holds a physician token) can send a hand-made verdict with every check set to `pass` and `auto_acceptable: true`. That saves a record whose real m4 verdict has flags. A `draft` or `flagged` record can also go straight to `saved` without the `/approve` step. The DB CHECK only requires an approver and a time, so it does not stop this.
- Status: the builder admits this in D-38 and open question 6. It is still the main gap between "the server enforces the gate" (brief, AGENT 6) and what the code does. Live attempt SG-1 is below.
- Fix: the server must load the latest verdict itself, from a server-side `verdicts` table written by the m4 job or the API, keyed by the DB record id plus a hash of `records.json`. It must never accept the verdict from the request body.

### F2 (minor): `app.audit_write` takes `app_role` and `user_id` from GUCs that the caller can change
- Where: `sql/040_audit.sql`. A session that can run SQL as any app role can call `set_config('app.role','physician',true)` and `set_config('app.user_id',<anyone>,true)`, then write audit rows in someone else's name. Raw SQL is needed (the API passes fixed arguments), so this is part of the documented residual risk. It still weakens the audit trail as evidence.
- Fix: work out the role inside the function from the caller (for example, give the app roles `INSERT` with an RLS `WITH CHECK (app_role = <map of current_user>)` instead of using SECURITY DEFINER), and log `session_user`/`current_user` as well.

### F3 (minor): the research export has no small-cell (k-anonymity) protection
- age_band + sex + encounter_month + encounter_type + pseudonym (which links all of one patient's visits) is unique for almost every patient in the seed (measured below). Builder D-37 already says this. The fix is to suppress or merge cells with k < 5 before export, or to drop sex/month for rare cells.

### F4 (minor): a consent withdrawal only takes effect when someone runs the export again
- `run_export` is a manual full refresh. There is no schedule and no trigger. Until someone runs it, the researcher still sees a patient who has withdrawn consent. The brief allows "removes them at the next export", but nothing guarantees that a next export ever happens.
- Fix: a trigger on `clinic.consents` (research_ok -> false) that deletes the matching rows, or a scheduled export plus a maximum-delay rule in the docs.

### F5 (minor): the connection pool does not reset session state
- `Database._put` only checks the transaction status. If a session-level `SET ROLE` or `SET app.*` ever runs (only possible through an injection, and none was found), it would stay on the pooled connection after COMMIT. Live attempt G-2 is below.
- Fix: run `RESET ROLE; RESET ALL` (or `DISCARD ALL`) in `_put`, or check `current_user = session_user` before reusing a connection.

### F6 (minor): the API does not check its own DB login at startup
- `API_DB_USER` can be set from the environment. Nothing refuses to start if that login is a superuser, has BYPASSRLS, or is the table owner. A wrong setting (for example, the bootstrap superuser) would put a superuser on the request path, and then any `RESET ROLE` escapes RLS.
- Fix: at startup, `SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = session_user`, and check that the login owns no tables in clinic/research. Exit if any check fails.

### F7 (minor): `.env.example` still has `POSTGRES_USER=owner_role` (builder's open item)
- Under Docker, `POSTGRES_USER` becomes the image's bootstrap superuser. Also, `config.py` always uses `POSTGRES_PASSWORD` as the owner_role password. If a Docker user follows the comment, the bootstrap superuser and owner_role end up with the same password.
- Fix (architect): set `POSTGRES_USER=mm_bootstrap` and add a separate `OWNER_DB_PASSWORD`. The Docker path is UNVERIFIED (I ran no Docker).

### F8 (minor, information): row counts and partial ids are visible through the catalog, EXPLAIN and the view
- Any app role can read `pg_class.reltuples` and the `pg_stat_*` views. `EXPLAIN ANALYZE` on the pharmacist view shows "Rows Removed by Filter" for the base table. All of this needs raw SQL. The view's `patient_ref` is the first 8 hex characters of the patient UUID. It is not a name, but it is a fixed partial identifier; a per-facility HMAC would be better.

The run rewrites the tracked `results/m5_backend/access_matrix_summary.json` (only `runtime_s` changed). I restored it with `git checkout`. Hygiene note: tests should not write tracked files.
- **SET vs SET LOCAL**: request, export and seed code use only `SET LOCAL ROLE` and `set_config(...,true)`. `030_views.sql` uses `SET ROLE ... RESET ROLE` inside the migration transaction (fine). See F5 for the pool.
- **Superuser/BYPASSRLS/owner on the request path**: none (RO-1, RO-5). The API logs in as `api_login` (NOINHERIT, memberships WITH SET only). See F6 for the missing startup check.
- **Parameterised SQL**: every `execute` in app/ uses `%s` binds. The only `sql.SQL(...).format(sql.Identifier(...))` calls build role or DB names from a fixed allowlist. No f-string SQL in app/.

- **Secrets**: `.env` is git-ignored (`git check-ignore`). ## Conditions D-80 must meet (per-flag "confirmed/edited" resolutions in the save request)

1. **The server owns the verdict.** The flags to resolve must come from a verdict stored on the server (written by the m4 job or the API, keyed by record id plus a hash of `records.json`). Never from the request body. This also fixes F1. A save request may only carry resolutions.
2. **Bind each resolution exactly.** `{check_id, field_path, decision: confirmed|edited}` must match a flag in that stored verdict one-to-one. Reject unknown ids, duplicates and missing flags. Reject the save if the record JSON hash changed after the verdict was computed (stale verdict).
3. **"edited" means re-verify.** An edited field changes the record, so the server must run m4 again on the new JSON (or store a new verdict). The save goes through only if the new verdict has no NEW flags.
4. **The resolver comes only from the token.** The resolver is `app.user_id` from the verified token, and it must be the approving physician (`approved_by = app.user_id()`, already enforced by RLS). `by` fields in the body are refused (extra="forbid"). Nurses and ASHAs cannot resolve.
5. **One atomic, append-only transaction.** The resolutions, the status change and the audit rows commit in one transaction. Store them in a new append-only table (same REVOKE plus trigger pattern as audit_log, FORCE RLS, INSERT policy only for physician_role in her facility). The audit row stores ids and enums only. Never store the field's value or free text (PII rule).
6. **No new free text.** If a "reason" is added (D-80 "what else"), keep it out of audit_log and out of the research export, and add it to the de-identification scan.
7. **Matrix cases.** Add access_case rows for: a forged verdict, a resolution for a flag that does not exist, a missing resolution, a nurse resolving, a resolution "by" another user, resolving after the record changed, and a cross-facility record. All must be denied.
8. **Critical flags (optional, recommended).** Require an extra step such as audio playback or a second confirmation for `critical` checks (dose and negation), so that clicking "confirm" without looking is less likely.
