### D-?: Accepting the "sub-family" reading of the dev/test split and freezing the test split   (Phase B / m1_data / orchestrator / 2026-11-10)
- What we needed to decide: The brief says "split by template family". The data builder made 9 categories (a to i, like "pharmacist dispensing") and, inside them, 22 smaller families of templates. Which of these is the "family" that must not appear in both dev and test?
- Options we considered: (1) Category = family. Pro: the strictest separation. Con: whole phenomena (for example cross-turn negation, category b) would exist only in dev or only in test, so the test could not measure them at all. (2) Sub-family = family, and every drug-dose combination also stays on one side. Pro: every phenomenon is tested; sentences that are near-copies of each other (same sub-family) never straddle the split. Con: dev and test share the broad sentence style of each category, so test scores may be a bit optimistic compared with brand-new kinds of sentences.
- What we chose: Option 2, as the builder proposed.
- Why: The point of the split is to stop near-duplicate sentences leaking from dev into test. Sub-families do that. Removing whole categories from test would make the main safety hypotheses (negation, doses) partly untestable. We accept that test sentences share a "style" with dev sentences and will say so in the report.
- What we actually did: Checked `uv run pytest m1_data/tests` (32 passed) and `mingw32-make split-lock` (OK). Committed data/ including data/splits/test.lock. From this commit on, the test split is FROZEN: any change to a test file or test gold label makes the split-lock check fail.
- What could go wrong / weaknesses: Test performance may overstate how well the system handles sentence types it has never seen. All Kannada text is not native-validated. Audio will be added later (task B1b); that pass may only ADD lines to test.lock.
- What else could be done: Hold out one entire category as an extra "unseen category" stress test and report it separately.
- How to change this decision later: data/splits/split_plan.json and m1_data's split code; any re-split must be a new, documented refreeze BEFORE the first `make eval-test` run, never after.
- Status: done
