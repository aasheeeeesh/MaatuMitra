### D-?: Security audit of m5: one real hole in the save gate, seven small ones   (Phase B / m5_backend / orchestrator / 2026-11-10)
- What we needed to decide: The simulated security auditor (reviews/m5_backend/2026-11-10.md, label ai_simulated_review) made 121 concrete break attempts against the database and API. What do we fix, and how?
- Options we considered: For the main hole (F1): (1) Keep accepting the verdict from the client and add a signature to it. Pro: small change. Con: the client still decides what the verifier said; signatures add key handling. (2) The server stores every verdict itself when the verifier runs, and the save request only refers to that stored verdict by id; the server then checks that every flag in the STORED verdict has a resolution from the approving physician (this merges with D-80). Pro: the client can no longer invent a clean verdict; matches the brief ("the API rejects saving a record whose verdict has unresolved flags"). Con: more work in m5 (a verdicts table, policies, tests).
- What we chose: Option 2 for F1, built together with D-80 in the m5 fix pass. All findings ACCEPTED; none rejected. F8 is partly deferred (see below).
- Why: F1 is the only attack that succeeded: in attempt SG-1 a physician saved a never-approved draft by sending a hand-made "all checks pass" verdict and got "200 saved". The safety gate is the heart of the project, so it must not trust the client.
- What we actually did: Validated the report against review_report.v1 (valid) and confirmed the sandbox database is stopped. Planned fixes for the m5 pass: F1 server-stored verdicts (with D-80 and the auditor's 8 conditions: server stores the verdict; each resolution matches exactly one flag; an edited field is re-verified; the resolver comes only from the token; everything written in one append-only transaction); F2 the audit function takes user and role from the database session role, not from settings the caller can change; F3 research export suppresses small groups (any combination of age band, sex, month and visit type with fewer than 5 patients is dropped or merged) - with our tiny synthetic seed this may leave the export nearly empty, which we will say honestly; F4 a consent withdrawal removes that patient's research rows immediately (trigger) instead of waiting for the next export; F5 the connection pool resets every connection when it is returned (so an injected `SET ROLE` cannot reach the next user); F6 the API refuses to start if its database login is a superuser, has BYPASSRLS or owns the tables; F7 .env.example stops using owner_role as the Docker superuser name; F8 patient_ref stops being the first 8 characters of the patient UUID (use a random or keyed reference). DEFERRED (documented residual limit): F8's row-count leak through EXPLAIN ANALYZE and table statistics, because it needs direct SQL access, which only someone holding raw database credentials has.
- What could go wrong / weaknesses: Confirmed holding (but by a simulated auditor): researcher and pharmacist could not reach base tables or other patients; all JWT attacks returned 401; mass assignment, SQL injection and audio IDOR were refused; the audit log could not be changed; 0 unauthorized successes in 1385 matrix cases; pip-audit clean. NOT done: gitleaks was not run (only a regex and exact-match scan of .env secrets, which found nothing); the Docker path was not run. The same AI wrote the expected-access table and the SQL, so the human should re-read the table.
- What else could be done: Add k-anonymity checks to the matrix tests; run gitleaks in CI (already in the workflow file, never run).
- How to change this decision later: m5_backend migrations, app save endpoint, export job, pool setup, .env.example.
